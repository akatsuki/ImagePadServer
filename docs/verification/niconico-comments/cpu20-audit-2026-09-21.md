# ニコニココメント書き出し：計測と24案の再監査

作成日: 2026-09-21。対象: 現在の作業ツリー、既存試作、保存済み計測結果。新しい速度ベンチマークや実機受入れを実施した報告ではない。

## 結論

前回の「libx264が主因」「24案は重複しない」という説明は強すぎた。確実なのは、保存済み1080p60試作で **FFmpeg側の受取待ちを含む `fwrite` 区間が長い** こと。デコード、scale、overlay、色変換、H.264、音声、muxのどこが支配的かは未確定である。

採用判断の前に、実アプリと同じ30fps・品質設定・アルファ解釈・GOPの基準を作り、書き出し全プロセスをまとめたCPU約20%の条件を実測する必要がある。現時点で大幅高速化の保証はしない。

実装計画は [nico-cpu20-performance-plan.md](../../../nico-cpu20-performance-plan.md)。品質を保つ経路を本線とし、画質変更・描画方式変更・プレーヤー変更は独立した条件付き候補にする。

監査で見つかった証拠の限界:

1. **CPU条件**: 前回は親PowerShellにaffinity=1を設定した。全子プロセスの実効affinity/Job所属/CPU使用率の成功run記録がない。8論理CPUで全対象が1論理CPUを共有するなら12.5%相当の時間容量だが、20% Job quotaとは並列性も予算も異なる。20%達成の検証済み結果とはしない。
2. **併用影響**: VRChat PIDの存在は確認していたが、VRChatのframe time、CPU/GPUの時系列は記録していない。快適に併用できることは未証明。`gpu_before` は実行前1点だけである。
3. **範囲**: ブラウザ起動、コメント画像/命令生成、HLS生成はこの試作比較の外。6秒を155秒へ線形換算しない。30fps本番の速度と直接比較しない。
4. **保存先事故**: 合成比較は別フォルダーへ保存する意図だったが、実際には元の `real-compose.json` と同名runを更新した。該当ファイルのmtimeは2026-09-21。9月17日の合成生ログとして再利用不可。古い結果は当時の検証文書を履歴として引用し、復元したことにしない。
5. **少数反復**: n=2/3かつVRChat負荷が変動。crop/instancedの採用優位を示さず、永続的な性能順位も確定しない。
6. **最新出力の検証**: この再計測について確認できるのは成功終了と保存物、前回のbaseline1に対するffprobeの6秒/360frame/H.264/AAC確認。9月17日の全decode/PTS/slice PASSを9月21日の出力へ流用しない。
7. **古い試作の失敗**: 一部の旧GCC helperは `0xc0000022`/timeout、再ビルドも未完了だった。CPUベンチマークから除外。PATH修正で原因が確定したとはしない。後続MSVC probeが動いたことも旧helperの失敗原因を説明しない。
8. **品質証拠の版**: 保存済みcrop品質JSONのEXE hashは `beed44c2...`、最新速度runは `85763ffd...`。過去の品質失敗は再試験の警告材料であり、最新実行物の品質判定を代行しない。

## 3. 既存実験から引き継ぐ知見

- [PNG/binary改善](performance-results-2026-09-16.md): 30fpsの全長実測は単発指示130.617秒、30frame batch118.297秒、batch+透明区間の可逆省略74.433秒、後日の再生成68.766秒。多くが各1回で負荷も異なるため、今回の60fps/1CPU試作と改善率を計算しない。透明画像だけのencoder下限診断も実コメントの代用にしない。
- [binary追加試験](performance-followup-2026-09-16.md): RLE、buffer再利用、filter thread固定の旧条件で採用改善なし。T4で再度threadを調べる理由は、今回の全プロセスCPU20%予算が旧試験と異なるためである。
- [sprite初期試作](sprite-spike-2026-09-16.md) と [追加試作](sprite-followup-2026-09-17.md): 前者の43.630→35.134秒は配信停止状態の155秒素材・各1回、後者のcombined32.616秒は2回平均。直接pipe、並行生成、3枚readback、可逆paletteの成果は現native経路の前提として保持し、再提案で新規効果と数えない。
- [native描画試験](native-render-2026-09-17.md): 過去のinstancedは全画素一致だが全体改善は小さく変動。cropはREAL最大差7/255、hardwareは最大差2/255で、その実装は品質条件を満たさない。
- [GPU全体合成](gpu-compose-2026-09-17.md): 元動画RGBAを追加pipeで送る方式はGPUコメントのみより18.2%遅かった。I420出力だけを見ると62.5%縮小するが、背景転送を含む総転送量は37.5%増加。U/V最大差13/255があり不採用。GPU内完結方式まで否定した試験ではない。
- [AVFrame試作](mask-avframe-2026-09-17.md): 同一プロセスの直接共有試作とshared SDKは既にある。REALの直接共有単独は約0.07%遅く、速度優位は未確認。背景は人工画像で元動画decode/Chrome生成を含まず、本番比較ではない。「libav経路は一切未実装」とする以前の時点の記述は更新が必要。
- [本番統合試験](native-integration-2026-09-17.md): WARP/pipe/可逆圧縮等の既存成果を保持する。低bit量子化・縁取り再生成を最適化に混ぜない。

前回24案で欠けていた優先項目:

- **全プロセス合算CPU予算と計測の実装**（T1/T2）。1コア固定・thread数だけで20%と認定しない。
- **decoder/filter/encoderのthread数最適化**（T4）。1CPUにencoder8threadsという条件の競合を解く。quality/bitstreamの変化も検査する。
- **fps正規化位置の検証**（T5）。無条件省略の代わりに、不要frameの高コスト処理を避ける。comment timestampと最終frameの同値性が条件。
- **PMA alpha契約の照合**（T3）。9月17日のGPU実験で `-alpha_mode premultiplied` 指定による差の縮小が報告されている。現在本番は明示なし、試作はoverlayにだけ明示。CLIの既定値推測で揃えず、既知画素で確定する。表示を修正した場合は基準を作り直す。

## 5. 根拠の扱いと一次資料

速度の根拠はローカルのargv/終了コード/タイマー/実行物hashとする。公式API資料は実装の可否の根拠であり、このPCでの改善率を保証しない。以下を2026-09-21に確認した。FFmpegの実オプションは同梱EXEのhelpでも照合する。

- [Windows Job CPU rate](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information): hard capの単位は百分率×100。20%は2000。上位Jobにも制限がある場合、下位の割合は親予算に対するものなのでOS全体20%と混同しない。
- [FFmpeg pipeline / option scope](https://ffmpeg.org/ffmpeg.html): decode/filter/encode/muxは別段階。thread等のオプションがどのinput/outputへ適用されたかをargvで確認する。
- [FFmpeg overlay](https://ffmpeg.org/ffmpeg-filters.html#overlay): alpha解釈、framesync、formatを揃える。
- [FFmpeg formats](https://ffmpeg.org/ffmpeg-formats.html): MP4 faststartは最終配置処理。必要性は直接MP4配信の契約に依存する。
- [D3D11 Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-map): CPUがresourceへアクセスする境界。CPUで測ったMap区間を実GPU計算時間と同一視しない。

この監査では製品コード、稼働アプリ、エンコーダー設定、Git履歴を変更していない。
