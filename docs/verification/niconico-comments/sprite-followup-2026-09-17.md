# ニコニココメント合成・追加最適化の実測

2026-09-17。`nico_sprite_spike` タグ専用の試験。通常サーバーには組み込まず、稼働プロセスも再起動していない。前回のスプライト試作を基準に、直接接続、生成との並行処理、3枚の読み出しバッファ、可逆パレットを比較した。

## 比較条件

- 素材: 前回と同じ約155秒、1280×720、30000/1001fps、362コメント。短尺は同素材の先頭6秒。
- 出力: 1920×1080、30fps、CPU libx264 veryfast / CRF 26 / AAC 160k。x264の1フレーム1スライス指定、フィルター、GOP、faststartを維持。
- コメント時刻: 既存FrameClockを維持。入力動画のfpsによって移動速度を変えない。
- 描画: D3D11 WARP。前回画素差の基準を満たさなかったハードウェアGPU経路は今回採用していない。
- 速度はブラウザー起動・命令作成・エンコード・MP4確定・HLS作成まで。全デコード／スライス検査は計測の外。
- 全試験を順に実行し、各回の前後に ingest/OBS/AirPlay が非稼働であることを確認。既存サーバー配下のFFmpeg 1個は存在したが、事前の2点で累積CPU時間は6.796875秒のまま。停止していない。
- 短尺は各方式3回、2周目は順序を反転。短尺のぶれを考慮して全長も別に比較する。前回と今回の絶対時間を直接比較しない。

判断: **今回の組み合わせを次の統合候補にする。** パレット化は無損失の転送量削減として有効。ただし短尺でパレット単独・3枚単独の速度優位は確認できず、画質やfpsを下げずに全体で約14%改善した、という範囲の結論とする。

## 白コメントと256色パレット

画像内の**RGBAの組**を数え、256種類以下かつ容量が減る画像を8bit index＋RGBAパレットにする。白い文字にも黒縁・半透明の画素があり、RGBだけを256色にして透明度を失う処理はしない。

256種類を超え、全画素がR=G=Bなら「濃淡8bit＋透明度8bit」にする。それ以外は元のRGBAに戻す。不可逆な色数削減は行わない。画像単位で方式を選ぶだけなので、白コメントと色コメントの重なり順は変わらない。

6秒の実画像13個は、パレット4個、濃淡＋透明度9個、raw 0個。画像データは2,071,948→988,122 bytes（**52.3%削減**）。数値はbase64化前の画像本体＋パレット。描画命令786,800 bytesは共通で、JSON／base64の付帯分は含めない。

全長235画像では、パレット42個、濃淡＋透明度122個、raw 71個。画像データは57,777,432→38,590,805 bytes（**33.2%削減**）。共通の描画命令4,663,900 bytesを加えた量では30.7%削減。圧縮方式の件数はコメント件数ではなく、キャッシュで生成された画像数である。

今回の圧縮区間はブラウザー→Goのスプライト画像転送。Goで完全復元してネイティブ描画に渡す。ネイティブ→FFmpegの全画面RGBAや、完成MP4の容量を半分にするものではない。このため転送量の削減率と変換速度の改善率は一致しない。

## 同一性と失敗処理

- 実JSの圧縮結果をGoで復元し、元RGBAとの完全一致を検査。透明、半透明、黒縁、色付き、256種類のパレット、257種類の白黒／色付き、raw復帰を含む。不正長、改行base64、余剰パレット、範囲外index、未知方式も拒否。
- 同じ実6秒の保存シーンで、ファイル／ストリーム入力×読み出し1枚／3枚の4通りを比較。180フレーム、各1,492,992,000 bytesの生RGBAが完全一致。SHA256: `705a0d428e8a350c3d17aa2366936fb9166ff2eabedbc98faed6440cbf24a664`。
- 同じ保存シーンで、Go中継／直接接続／直接接続＋3枚の全180デコードフレームが一致。framemd5ファイルSHA256: `2FB6AF645A6EBD8CB9DD659DD6AF312CABF2DCF8DA1E493F8E27A8521226ADFC`。
- パレット＋3枚の出力と、同一ブラウザーの従来WebGL描画を比較。実180フレームの最大差1、平均絶対差0.000011。色付き・上下固定・複数行の合成fixture 80フレームも最大差1。前回の許容差1を変更していない。
- 1/2/3/5/31フレームで順序と末尾排出を検査。途中切断、終端欠落、終端後の余剰データを拒否。
- FFmpeg失敗、native失敗、生成失敗、キャンセル、各プロセス起動失敗の6ケースで速やかな終了を確認。開始成功した子プロセスはそれぞれ一度Waitして回収する。

## 形式・実装上の範囲

NPS1は全シーンのファイル、NPS2は版付きヘッダー＋長さ付きバッチ＋明示終端。1バッチは最大30フレームで、送信が詰まると次のブラウザー要求を止める。画像IDと命令順を維持し、テクスチャ全体は最大512MiBに制限する。これはまだ長時間動画向けのテクスチャ解放設計を備えていない試作である。

3枚の読み出しでは古いスロットを先にMapする。Map(flags=0)の完了待ちを使い、最後の1〜2枚も順に排出する。[Microsoft Map資料](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-map)。直接接続には`*os.File`のパイプハンドルを渡し、GoのRGBAコピーgoroutineを省く。[Go os/exec資料](https://pkg.go.dev/os/exec#Cmd)。

試験スクリプト: `scripts/experiments/test-nico-sprite-followup.ps1`（fixed / screen / full）。素材・ログ・出力は `%TEMP%/imagepad-nico-perf-20260916/followup-20260917`。速度だけで正式導入とせず、通常アプリへの統合、進捗表示、長時間・高密度コメント、配布とライセンス、VRChat実機は別の確認範囲とする。

実装レビューでは、通常経路へ組み込む際の「失敗出力の扱い」と「生成／デコードフレーム数の照合」が挙がった。現在の試験は`t.TempDir`内の出力を使い、失敗すると直ちに試験失敗として削除し、検査成功時だけ指定先へ保存する。正式導入時も、作成途中ファイルを完成品として登録しない既存の条件を維持する必要がある。
