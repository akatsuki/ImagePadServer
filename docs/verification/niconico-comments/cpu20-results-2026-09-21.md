## T11 CDP初期化修正と候補比較

`Page.enable`は使用中のCDP commandに必須ではなく、Windows ChromiumではGPU helper終了と接続切断を誘発していたため、production既定経路から外した。最小HTML probeはJob外・CPU20% Job内ともRuntime.evaluate、layout、screenshotまでPASSし、固定6秒browser productionもMP4/HLSの全decode、PTS、AU 1slice、HLS keyframe検証までPASSした。

修正後の独立full run `build/nico-cpu20/t11-page-enable-default-full-20260921a/` は33件を実行し、6件complete・27件failed。固定6秒Aは通過し、失敗理由はnative Bの`WebGL2 renderer required`、高密度snapshot path指定ミス、実素材の生成4649に対するdecode4647だった。GPU helper切断が全件を占める状態からは脱したが、VRChat frame timeは未取得で受入れはpendingである。

SwiftShader候補では `build/nico-cpu20/t11-swiftshader-fixed-20260921a/` と `build/nico-cpu20/t11-swiftshader-high-density-20260921a/` を実行した。各11件がcomplete、CPU20% Jobは全件`verified=true`。browser A対native Bのpaired短縮は、固定6秒でwall約23〜25%・CPU秒約25〜32%、高密度10秒でwall約35〜40%・CPU秒約42〜44%だった。これは候補比較であり、GPU/VRChat実機ゲート未確認のため既定採用へは昇格していない。

## CPU20%実動画試験

`build/nico-cpu20/production30-20260921e/runner-report.json` のbrowser backend、duration 1000ms、1920x1080、30fps、Job CPU rate 2000は、対象Jobの `verified=true` まで到達した。しかしframe 0受信が約20秒で `i/o timeout` となり、出力は10 bytesの既存置換用ファイルだけだった。これは性能PASSでも品質PASSでもない。

同じworker executableを320x180/1秒のsynthetic sourceでnative backendへ明示compositor path付き起動したrun（`build/nico-cpu20/worker-native-smoke-20260921/runner-report-native-explicit.json`）は、native-warp選択とJob `verified=true` までは確認できたが、compositorの `truncated scene` とWebSocket切断で失敗した。自動embedded pathは standalone buildで `native compositor is not embedded` となった。いずれもnative workerの成功E2EやHLS公開の証拠にはしない。

切り分けのため、同じ小解像度browser binary transportをJobなしでも実行したところ、現在のChrome環境では従来の `--disable-gpu` 経路が約1秒でWebSocketを強制切断した。診断stderrにはGPUプロセスの `exit_code=-1073741790` と `GPU process isn't usable. Goodbye.` が出ており、CPU20% Job内でも同じ終了を再現した（`build/nico-cpu20/browser-smoke-20260921b/runner-report.json`）。`--disable-gpu-sandbox` 単独、およびSwiftShader併用では強制切断は避けられたがreadbackが約20秒停止したため、採用せず元の起動引数へ戻した。`--no-sandbox` は試していないし、追加しない。診断時だけ `IMAGEPAD_NICONICO_RENDER_DEBUG=1` でChrome stderrを親へ流すフックを残した。

native backendのCPU20%試験で見えた `truncated scene` は、browser生成側の失敗後に入力pipeを閉じた二次エラーだった。埋込みcompositorへ既存の小型NPS3 fixtureを直接流す試験は終了コード0でraw出力を生成し、payload/source/manifestのhash検査もPASSした。さらに実験用feeder経由で321x181・120フレームをCPU20% Job内へ流し、`status=complete`、`verified=true`、raw 27,888,480 bytesを確認した。これはcompositor単体のCPU20証拠であり、browser生成を含むnative E2Eの証明ではない。browser生成失敗時の本番runは速度比較母集団へ入れない。

## T11観測ゲート

`scripts/experiments/nico-native-probe/t11_observe.py`を実production executorへ接続した。各caseのrunnerをCPU20% Jobで実行しながら、`observation.json/jsonl`へ次を保存する。

- runnerと取得できた子プロセスのPID、累積CPU秒、WorkingSet、Handle数、終了後の残留PID
- `nvidia-smi`のGPU使用率、エンコーダ使用率、VRAM使用量
- 実行中の`VRChat`プロセスの存在、PID、CPU/WorkingSet観測、未取得のframe time
- timeout/終了コードと、観測バックエンドの欠測理由

このWindows環境では`Win32_Process` WMIがアクセス拒否となったため、`Get-Process`へフォールバックした。フォールバックは親PIDを提供しないので、子ツリー残留の完全判定は保留し、CPU20% Jobの所属・CPU秒は`runner-report.json`を正とする。VRChatのframe timeは一般プロセスAPIから取得していないため、`vrc_acceptance_pending=true`を必ず保持する。

実観測run `build/nico-cpu20/t11-observe-20260921e/`では、固定6秒browser warmupがGPU/WebSocket境界で失敗したが、CPU20% runnerは`verified=true`、観測は3サンプル、観測CPU 0.015625秒、観測範囲内の残留PIDなし（ただし親ツリー完全性がないため`child_residue.clear=null`）、GPU/VRAM取得、VRChat検出あり・frame time未取得だった。`report.json`の`observation_gate`は1 observed / 32 missing / `child_residue_incomplete_cases=1` / VRChat gate pendingで、`matrix_complete=false`・`acceptance_complete=false`であり、失敗runを性能PASSへ読み替えていない。

`t11_report.py`はこのrunについて、観測CPU秒・WorkingSet・Handle・GPU使用率・VRAMのmin/max、CPU20 Job `verified`数、budget未検証数まで`observation_summary`/`observation_gate`へ出力する。入力snapshot/sourceとrunner/test/FFmpeg/helperのSHA256もcase結果へ保存するため、後から別実行物の数値へ置換できない。

native Bのhelper切り分けでは、CPU20 native-postで成功した明示helperを`--compositor`で指定した。helper自体の準備は通ったが、production pipelineは依然としてbrowser sprite captureを必要とし、CDP/GPU境界で失敗した。誤って失敗生成物`out.mp4`を入力にした試行は証拠から除外し、正しい実素材`source-6s.mp4`で再実行したrunもbrowser capture失敗となった。SwiftShader＋GPU in-processの診断も実CPU20 Job内で21.39秒のCDP readback timeoutとなったため、既定runtimeは変更していない。

追加のブラウザ差分確認では、Playwright Chromium本体がGPU helper終了`-1073741790`、Playwright headless shellが必要DLL欠落`-1073741515`、`single-process`が21.10秒のCDP timeoutとなった。いずれもCPU20 Jobの`runner-report.json`を保存し、T11採用候補には入れていない。executorには`--browser`を追加し、指定ブラウザの実行物hashをcaseへ保存する。

## CDP失敗位置の固定化

`IMAGEPAD_NICONICO_RENDER_CDP_TRACE=1`を追加し、CDP呼び出しごとのメソッド名・経過時間・エラーをstderrへ記録するようにした。既定値では無効で、ブラウザ起動引数や本番経路は変えない。Playwright Chromiumを指定した新しいCPU20%固定6秒runでは、`Page.enable` 約337.2msの直後にWebSocketが強制切断され、stderrには次の因果順が保存された。

1. GPU process exited unexpectedly: `-1073741790`
2. GPU process isn't usable. Goodbye.
3. `Page.enable` WebSocket disconnect

このrunでは`Runtime.evaluate`へ到達していない。`t11_execute.py`はstderrを`browser_gpu_process_unusable`としてcaseへ保存し、`t11_report.py`はfailure classを集計する。`build/nico-cpu20/t11-failure-class-20260921a/report.json`は1 failed、32 missing、`failure_classes.browser_gpu_process_unusable=1`、`complete=false`である。これにより`truncated scene`を根本原因と誤認せず、browser GPU helper終了とpipe close後のnative二次エラーを分離できる。

同時点で`PresentMon.exe`は見つからず、VRChatプロセスは稼働中だった。一般プロセスCPU/GPU/VRAMは取得できるがframe timeは取得できないため、VRChat併用ゲートは引き続きpendingである。
実素材SwiftShader warmup `build/nico-cpu20/t11-swiftshader-real-warmup-20260921a/` はCPU20% Job `verified=true`で完走したが、生成4649 frameに対してdecode4647 frameとなり`artifact_validation_failed`。この差は既存契約どおり無条件に許容しない。

executorには高密度snapshot/sourceの起動前存在検査を追加し、欠落時は `snapshot_missing` / `source_missing` として保存する。直近のPython実験テストは40件、T11対象は25件でPASSしている。

`scripts/experiments/nico-native-probe/t11_stability.py`を追加し、raw frameを保存せずnative compositorへ同じ実素材NPS3を繰り返し投入できるようにした。`build/nico-cpu20/t11-native-stability-smoke-20260922a/`でCPU20% Job下の60秒スモークを実行し、36/36回がexit 0、observer 61 samples、peak WorkingSet 8,814,592 bytes、peak handles 134、native reportのduration 60.125秒を記録した。runnerは`verified=true`・`job_cpu_rate=2000`・CPU秒97.890625だった。

この環境ではWMIが拒否されGet-Process fallbackになったため、observerの`child_residue.tree_complete=false` / `clear=null`は仕様どおりであり、Job reportのPID/CPU所属を正とする。VRChatの新規Performance Statsは取得できず`vrc_acceptance_pending=true`。これはnative層の60秒切り分けであり、30分反復、browser/worker統合成功、VRChat受入れPASSへは昇格させない。記録は`build/nico-cpu20/t11-native-stability-smoke-20260922a/stability-report.json`に保存した。

30分反復も同じnative-onlyハーネスで実施した。`build/nico-cpu20/t11-native-stability-30m-20260922a/`はduration 1,800.828秒、1,088/1,088回exit 0、timeout 0、CPU20% Job `verified=true`・`job_cpu_rate=2000`、CPU秒2,912.328125だった。8論理CPU換算の総CPU量は約20.22%、observerは1,802 samples、WorkingSet 8,708,096–16,334,848 bytes、handle 128–141、最大プロセス数1、終了後のrunner/compositor/profile残留0件。WMI fallbackのためchild tree判定は不完全で、開始時からVRChatが不在だったためVRChat gateはpending。30分native安定性は確認したが、browser/worker統合・VRChat併用受入れ・全raw parityの完了には使わない。

## 現行ソースのA/Bベンチマーク（2026-09-22）

元のbrowser backend（A）と現行native backend（B）を、現行ソースから`nico_native_embedded`付きで再ビルドした同一workerで比較した。CPU制約は両方ともWindows Jobの20%上限（8論理CPU、`job_cpu_rate=2000`）で、実行結果の`verified=true`を確認している。採用runは`build/nico-cpu20/t11-current-ab-benchmark-20260922b/`である。

固定6秒素材はA/Bを5ペア実行し、MP4/HLSのdecode、PTS、単一slice、HLS先頭keyframe、runner検証を全11完了ケースでPASSした。中央値はAが15.0444325秒、Bが13.0436318秒で、処理時間ベースの高速化は**13.30%**（約1.153倍）だった。CPU秒の中央値はA 17.921875秒、B 14.8125秒で、CPU使用量は**17.35%削減**された。

同じ155秒実素材では、warmup後の代表1ペアを実行した。Aは255.6260333秒、Bは214.6389172秒で、処理時間ベースの高速化は**16.03%**（約1.191倍）、CPU秒はA 314.015625秒からB 247.75秒へ**21.10%削減**となった。両成果物ともMP4 4649 frame/30fps、PTS/decode/AU 1 slice、HLS 39 segment・先頭keyframe・decodeをPASSしている。ただし長尺はまだn=1の代表値であり、最終性能値には固定6秒n=5の13.30%を主値として扱う。VRChat併用frame-time gateと30分統合受入れは別途未実施である。

### native内部ステージ分解（計測入り現行バイナリ）

`build/nico-cpu20/t11-current-timing-benchmark-20260922a/`で、native側の`native_sprite_stream`（sprite/NPS3生成）、`native_compositor`（WARP compositorプロセス）、`native_ffmpeg`（FFmpegプロセス）を追加計測した。これらは並行実行されるため、値を合計しない。プロセス寿命には上流入力待ち・下流への書込待ち・CPU予算待ちも含まれ、最長区間だけでボトルネックは判定できない。

固定6秒5ペアの中央値は、sprite 6.751秒、compositor 6.805秒、FFmpeg 6.886秒、全体`native_render_encode` 6.887秒だった。155秒実素材の代表1ペアでも、sprite 110.040秒、compositor 110.055秒、FFmpeg 110.158秒、全体110.159秒となった。終了時刻は近いが、逆圧でも同じ形になるため「3経路の負荷が均衡」「FFmpeg以外は誤差」とする当初の解釈を訂正する。追加の切り分け結果は`ffmpeg-bottleneck-investigation-2026-09-22.md`を参照。

GPUエンコーダー使用率は0%、GPU使用率も最大3%以下だったため、現行の次の調査対象はGPUではなく、CPU側のlibx264処理とRGBAフレーム転送、ならびにWARP compositorのCPU負荷である。今回の計測は原因をこの3区間まで絞ったもので、各プロセス内のx264・WARP・JSON/zlibの内訳までは未分解である。

### PID別CPU追加計測（固定6秒・A/B各5回）

プロセスごとのCPU帰属を追加するため、observerの1秒サンプルにPID、プロセス名、累積CPU秒、Working Set、handlesを保存するようにした。`build/nico-cpu20/t11-process-attribution-20260922b/`で、同じCPU20% Job・同じ固定6秒素材をA/B交互順で5反復した。

全10測定ケースはrunner `verified=true`で、MP4/HLSのdecode、PTS、単一slice、HLS先頭keyframeをすべてPASSした。中央値は次のとおり。

- browser A: wall 19.809秒、Job CPU 20.125秒、平均観測CPU 17.455%。
- native B: wall 17.869秒、Job CPU 17.250秒、平均観測CPU 17.273%。
- BはAよりwallで**9.79%高速化**、Job CPU秒で**14.29%削減**。

PID別CPU秒の中央値は、AがFFmpeg 7.297秒、Chrome 6.016秒、worker 1.469秒。BはFFmpeg 6.703秒、Chrome 1.547秒、`nico-compositor.exe` 1.562秒、worker 0.578秒だった。つまりnative化でChromeの観測CPU負荷を約74%削減できている。一方、FFmpeg合算には書き出し用に加えてHLS作成・decode等の検証プロセスも含まれるため、この数値をlibx264単独の負荷とは扱わない。BではcompositorのCPUが追加されるが、Chrome削減分を大きく下回る。書き出し用FFmpegの切り分けは追加調査で実施した。

なお、PID別値は1秒サンプリングのfirst-seenからlast-seenまでの差分で、終了直前のCPU時間を含まない可能性がある。したがってプロセス別合計は帰属の下限値として扱い、総量の判定はWindows Jobの`cpu_seconds`を正とする。今回のobserverではVRChat PIDを検出したが、Performance Statsのframe timeは取得できず、VRChat併用受入れは`pending`のままである。GPU全体使用率は中央値約31%、最大38%（VRChat等を含むシステム全体）だった一方、GPUエンコーダー使用率はA中央値0.69%、B中央値0.38%、各最大1%だったため、ハードウェアエンコードがボトルネックとは扱わない。
