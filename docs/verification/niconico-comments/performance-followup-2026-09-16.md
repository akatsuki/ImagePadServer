# コメント付き変換：画質を維持した追加最適化の結果

2026-09-16。ユーザー指定は「今の画質設定を維持して最適化を続ける」。CPU libx264、CRF 26、veryfast、1080p/30fps、AAC 160k、コメント件数・FrameClock・H.264の1フレーム1スライスを維持する。

## 結論

追加の圧縮・メモリ再利用・フィルタースレッド調整では、採用できる変換時間の短縮を確認できなかった。試作コードは本番経路へ採用せず、既存の30フレーム指示＋ゼロRGBA区間の可逆圧縮を維持した。同じ約155秒素材について、前回の全長実測68.766秒／74.433秒を更新する成果はまだない。

別途、ブラウザー終了時の出力パイプ待ちを避ける変更を加えた。これは終了処理の改善であり、フレーム処理速度の向上とは分けて扱う。稼働アプリは今回再起動しておらず、この修正は稼働中バイナリには未反映。

## 比較条件と結果

入力・ツール版は[前回の実測記録](performance-results-2026-09-16.md)と同じ。固定の6秒・180フレーム、1080p/30fpsを使用。ダウンロードは含めず、pipelineはブラウザー初期化からMP4完成・HLS作成までを測る。描画単体の測定は初期化・エンコードを除外し、単発指示を使用するため、pipelineの時間と直接比較しない。

| 試作 | 実測 | 判断 |
|---|---|---|
| ブラウザーのGPU有効化 | 描画単体3.384秒→3.235秒、各1回 | 小さい差。変換全体・画素比較未実施のため未採用 |
| 同色連続区間も圧縮するRLE | 描画単体3.596秒、転送量325.9MB→235.0MB | 転送は減ったが処理時間は改善せず、未採用 |
| ブラウザー側バッファ再利用 | pipeline中央値7.139秒→7.290秒、交互に各3回 | 改善せず、未採用 |
| FFmpeg合成スレッド数の指定 | 1スレッド11.543秒、2スレッド8.079秒、4スレッド8.322秒、各1回 | 自動設定の上記実測より遅く、未採用 |

バッファ再利用なしは6.6385／7.4047／7.1393秒、ありは7.2900／7.3091／6.8768秒。比較中もOS・他アプリの負荷や温度は固定していない。短い区間での結果であり、他素材・全長に効果がないと証明したものではない。

GPU試作でもエンコーダーは変更していない。WebGLが報告した描画バックエンドは、既存設定がANGLE Microsoft Basic Render Driver D3D11、有効化時がANGLE NVIDIA GeForce RTX 5070 Ti D3D11だった。GPUを有効化すれば大幅に速くなるという根拠は得られていない。

試作段階では、小fixtureでRLEと既存fullの80フレーム画素一致、再利用バッファの45フレーム画素一致・2枚の先読み制限も確認した。ただし速度の採用条件は満たさなかった。RLE・GPU・バッファ再利用・スレッド指定の内部オプションと試作専用テストは取り除いた。

## 終了待ちの変更

初回プロファイルでは`browserSession.close`内で約12.73秒の待ちを観測した。このプロファイルはユーザーの変換と重なって取得されたため、変換総時間31.106秒を正常時の性能比較には使わない。

ブラウザーの`exec.Cmd.Stdout/Stderr`に`io.Discard`を指定すると、Goは出力コピー用のパイプとgoroutineを作る。子プロセスに保持されたパイプが閉じるまで`Wait`が待つ構造になる。nilのままにするとOSのnullデバイスへ直接接続されるため、破棄していた出力の扱いを保ちつつ、このパイプ待ちを避けられる。ローカルGoの`src/os/exec/exec.go`にある`writerDescriptor`・`awaitGoroutines`を確認した。

`startBrowser`はStdout/Stderrをnilのままとした。性能診断には実際のWebGLバックエンドと`close_ms`を追加し、以後は描画ループと終了処理の時間を分けて観測できるようにした。毎回12.73秒短くなるとは判断しない。

試作を除去した最終状態の180フレーム診断はPASSし、初期化1.083秒、描画ループ4.069秒、終了処理0.285秒だった。初回プロファイルと同一負荷ではないため、12.73秒との比率を速度改善率には使わない。初回の待ちが`os/exec.(*Cmd).awaitGoroutines`の`goroutineErr`受信で発生していたこともブロックプロファイルで確認した。

## 次に実証すべき境界

現状はブラウザーからの転送を圧縮しても、Goで全画面RGBAへ復元し、FFmpegへ毎フレーム渡している。1080pは1枚8,294,400バイト、4649枚で約38.56GBになる。これはGo→FFmpegへの論理画素量であり、WebSocket上の圧縮後通信量やピークメモリではない。

次の大きな候補は、既存ライブラリの文字組み・衝突判定・時刻処理を維持し、文字画像を一度転送して、各フレームでは位置・クリップ・透明度などの描画指示を受け渡す方式である。ネイティブ側で合成し、最終的なCPU libx264と画質設定を保つ。通常文字だけを別字幕方式へ置換する案にはしない。

これは未実装の構成案であり、速度向上は未測定。既存bundleが使う描画状態を欠落なく取り出せること、CA・装飾・縦横・重なり・スクリプトの画素比較、色変換・同期・実圧縮出力の1スライス検査が必要になる。小さな設定変更を重ねる段階から、画像の受け渡し方法を検証する段階へ移る判断材料とする。

その後のユーザー指示「それテストしてみて」に基づく、文字画像＋描画命令の試作と実測は[文字画像再利用方式の試験](sprite-spike-2026-09-16.md)に記録した。本番導入とは区別する。
