# IPv4/IPv6回線診断とRTSP公開先選択の設計

## 目的

ImagePadServerに次の機能を追加する。

1. 設定画面から端末の回線経路とUPnP IGDの利用可否を診断する。
2. IPv4/UPnP、IPv6直接接続、既存のLAN/Tailscale候補から、RTSP公開に最適な接続先を自動選択する。
3. 外部到達性を確認できない場合に、公開済みと誤表示しない。

既存のセッション単位のRTSPマッピング管理、HLS動作、保存済みレイテンシーモードとの互換性は維持する。

## 対象範囲

### 今回実装するもの

- 読み取り専用の経路、ネットワークインターフェース、IPv4、IPv6情報の取得。
- SSDP探索と、WANIPConnection/WANPPPConnectionサービスへの読み取り専用SOAP問い合わせ。
- `/api/network-diagnosis` と `/api/state` の `networkDiagnosis` による構造化診断結果の提供。
- 設定画面の診断ボタンと、結果を表示するダイアログまたはパネル。
- 既存UPnP処理を利用した明示的な一時ポートマッピング試験。
  - 作成、照合、削除を行う。
  - 動作中のRTSPマッピングを置き換えない。
- RTSP公開候補の自動選択。
  - グローバルIPv4 + UPnPマッピング成功。
  - グローバルIPv6での直接接続。
  - 設定済みのLAN/Tailscaleアドレス。
- `net.JoinHostPort` による正しいIPv6付きRTSP URL生成。
- 実ルーターや外部サービスを必要としない候補選択・待受・失敗テスト。

### 今回は実装しないもの

- Windows Defender Firewallルールの自動作成・削除。
- ルーターのIPv6ファイアウォールピンホールの自動設定。
- PCP、NAT-PMP、UPnP IGD v2のIPv6ファイアウォール制御。
- RTSPリレーサービス。
- 端末がグローバルIPv6を持つだけで、外部到達可能と断定すること。

## 構成

### `internal/network`

読み取り専用のローカルネットワーク情報APIを追加する。デフォルト経路、インターフェース情報、ローカルIPv4、IPv6アドレス、アドレスの用途、グローバルユニキャスト候補かどうかを返す。

この処理は、経路、ファイアウォール、ネットワークアダプター、DNS設定を変更しない。

IPv6は少なくとも次の種別を区別する。

- ループバック
- リンクローカル
- ULA（ユニークローカルアドレス）
- 未指定
- マルチキャスト
- グローバル
- 不明

一時IPv6やプライバシーIPv6も候補にはできるが、動作中のセッションを超えてアドレスを保存しない。

### `internal/upnp`

UPnPの探索とマッピング所有権は既存どおりこのパッケージに置く。診断APIでは、次の情報を返す。

- UPnP機器名
- 検出されたWANサービス
- 接続状態
- ルーターが返した外部IPv4
- NAT/CGNATの分類
- 実行できた読み取り専用操作
- サニタイズ済みエラー

診断APIと動作中のマッピングAPIは、低レベルのSSDP/SOAP処理だけを共有する。読み取り専用診断では、ポートマッピングを作成・削除しない。

明示的なマッピング試験は所有対象を記録し、成功後は必ず削除を試みる。

既存の `upnp.Result` はRTSP公開との互換性のため維持し、詳細診断用の型を別に追加する。

### `internal/obsrtmp`

RTSP準備完了通知に、公開ホストに依存しない情報を持たせる。

- セッションID
- 世代番号
- MediaMTXパス
- RTSPポート
- 使用トランスポート
- 待受準備状態

公開URLの組み立てはMediaMTX内部ではなく、公開候補を選択するサーバー側で行う。

MediaMTXはIPv6でRTSPを待ち受けられるように設定・テストする。ただし現在のTCP専用設定は維持し、IPv6対応を理由にUDPを有効化したり、レイテンシーモードを変更したりしない。

### `internal/server`

RTSP公開先を選ぶプランナーを追加する。入力は次のとおり。

- MediaMTXのRTSPエンドポイント
- ローカルネットワーク情報
- UPnP診断・マッピング結果
- 設定されたホスト優先順位
- 将来追加する外部到達性確認結果

プランナーは候補一覧、選択された候補、選択理由を返す。ファイアウォールやルーターの設定変更は行わない。

選択順序は次のとおり。

1. グローバルIPv4を返す、照合済みのUPnPマッピングを優先する。
2. 公開IPv4が使えない場合、IPv6でRTSP待受が準備できていればグローバルIPv6を候補にする。
3. 外部プローブが成功していないIPv6は「外部到達性未検証」と表示する。
4. 公開できない場合は、設定済みのTailscale/LANアドレスをプライベートな代替候補にする。
5. 有効な公開候補がない場合、誤解を招くRTSP公開URLを表示しない。既存のHLS動作は維持する。

IPv6はIPv4用UPnPマッピングとして扱わない。URLは `net.JoinHostPort` で生成し、次の形式にする。

```text
rtsp://[2001:db8::1234]:8554/session-path
```

リンクローカルとULAは、公開候補として扱わない。

既存のセッションID・世代番号チェックをそのまま有効にする。古いRTSP準備完了通知が、新しいマッピングや公開URLを上書きしてはいけない。セッション終了時には、ImagePadServerが所有するIPv4マッピングだけを削除する。

### 診断APIと設定画面

認証付きの `POST /api/network-diagnosis` を追加する。ハンドラーは期限付き・キャンセル可能な診断処理を実行し、構造化結果を返す。

診断結果は `/api/state` と状態イベントにも返すが、恒久的なネットワーク設定として保存しない。

設定画面には、既存のネットワーク速度チェックの隣に `回線・UPnP診断` ボタンを追加する。結果には次を表示する。

- 端末側の経路
- IPv4/IPv6候補
- UPnP機器とサービスの状態
- 外部アドレスの種別
- RTSP公開の推奨結果
- 注意事項

ポートマッピング試験は別操作にし、ルーター設定を変更することを確認するダイアログを表示する。`未検証` と `失敗` は別の状態として表示する。

## データの流れ

```text
設定画面
  -> POST /api/network-diagnosis
  -> network.Snapshot + upnp.Diagnose
  -> サーバーの診断結果
  -> JSON応答 + state/SSE

MediaMTXのRTSP準備完了
  -> サーバーの公開候補プランナー
  -> IPv4用UPnPマッピング または IPv6直接接続
  -> セッション確認済み公開RTSP URL
  -> OBS/ラジオ状態と通常の共有URL
```

診断APIはユーザー操作時だけ実行する。起動時は既存の安全メッセージを設定し、SSDP/SOAP処理を同期実行しない。

RTSP公開処理は、動作中セッションに必要なマッピング処理だけを行い、RTSP準備完了コールバックをネットワーク探索で長時間ブロックしない。

## エラー処理と安全性

- すべてのネットワーク処理に期限とキャンセルを設定する。
- SSDPタイムアウト、SOAP失敗、WANサービスなし、CGNAT、IPv6ファイアウォール不明、外部プローブ失敗を別状態にする。
- URLの認証情報、SOAP本文、資格情報、無関係なルーター設定をUIやログに出さない。
- 一時マッピング作成後は、すべての戻り経路で削除を試みる。
- 削除失敗は警告として残す。
- 今回はファイアウォールやルーターの自動変更を行わない。
- 起動時・終了時の掃除は、ImagePadServerが所有するRTSPマッピングだけを対象にする。

## テスト

### ネットワークとUPnP

- IPv4、グローバルIPv6、ULA、リンクローカル、ループバック、マルチキャスト、CGNAT、未指定アドレスの分類テスト。
- 必要なOSコマンドがない場合や、出力が不完全な場合の経路情報テスト。
- 固定されたSSDP、機器XML、SOAP応答による解析テスト。
- 読み取り専用診断が `AddPortMapping`/`DeletePortMapping` を呼ばないこと。
- 明示的なマッピング試験が成功後に所有マッピングを削除すること。
- 削除失敗を結果に表示すること。
- SOAPエラーコードを安定した診断カテゴリに変換すること。

### 公開候補プランナー

- 検証済みでグローバルなIPv4 UPnPがある場合、IPv4を優先すること。
- IPv4が使えず、IPv6待受が準備済みならIPv6を選ぶこと。
- IPv6 URLを角括弧付きで生成すること。
- ULA、リンクローカル、CGNATを公開候補から除外すること。
- 未検証のIPv6を外部到達可能と表示しないこと。
- LAN/Tailscaleへのフォールバックを維持すること。
- 古いコールバックが新しい候補やマッピングを上書きしないこと。
- セッション停止・モード変更時に所有マッピングだけを削除すること。

### サーバーとUI

- 診断APIが既存の管理者アクセス制御を要求すること。
- 診断結果が返され、保存されずに更新されること。
- UIが不明・未検証・失敗を区別して表示すること。
- マッピング試験に確認操作が必要なこと。
- 既存の速度チェックとHLS/RTSP共有URLが退行しないこと。

## 段階導入

第1段階では、診断API/UI、IPv6検出、IPv6対応RTSP URL生成、未検証状態を含む公開候補選択を実装する。既存のIPv4 + UPnPを優先する。

将来は、次の機能を同じ候補モデルに追加できる。

- Windowsファイアウォールプロバイダー
- ルーターのIPv6ピンホール/PCPプロバイダー
- 外部到達性確認プローブ
